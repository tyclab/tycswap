# Changelog

## Since v0.24.1

- **Fixed:** Temporary files that a killed tycswap process left in the backup store are removed. A write goes through a `.atomic-*.tmp` file beside its target and renames it into place; a process killed in between, such as a status line Claude Code timed out, left that file behind for good, mode 0600, a copy of a state or config file. Every scheduled auto-switch round, on or off, now removes such files older than an hour anywhere in the backup store, following no symbolic link inside it, and logs `Removed N stale temporary files` when it removed any (DESIGN A128).
- **Fixed:** `tycswap.log` no longer fills with the warning `live config names slot X (…) but the live credential is slot Y's (…); using Y. A running Claude Code may have rewritten ~/.claude.json` while a session runs on an account's own Mythos login. Such a session writes its account into the shared `~/.claude.json`, and every auto-switch tick, status line and hook logged the line again, about 100 times in half an hour with one Mythos session open. tycswap already took the right account from the credential; the line is now logged at DEBUG when the config names an account with a signed-in Mythos login, as it already was for the Fable store's account, and stays a warning otherwise (DESIGN A127).
- **Fixed:** A start on Linux and WSL no longer switches or holds the default login or the Fable store when a start login has a Mythos login of its own. Until now a start whose shared login sat on an account that is no start login switched that login to one, one at its limit included, and a start on a start login at its limit held it there: every session on that login ran on that account meanwhile and answered with its limit. 0.25.1 ended this for a Fable start only while the default login sat on a start login with room. Such a start now comes up on the start login's own Mythos login (`tycswap start: Account-9 is no start login; starting on start login Account-8's Mythos login.`), for a session of any model, fresh, resumed or in print mode, and its SessionStart hook moves it to the default login, the Fable store or a Mythos login. A session that came up this way leaves the Mythos login at its hook also when its destination is at a limit, and one auto-switch tick then moves that login on. With no start login's Mythos login ready, with `--account`, and on Windows and macOS a start selects as before (DESIGN A125).
- **Fixed:** On Linux and WSL the first Mythos or Fable start after a login's token had expired sent its first message from the login it came up on, a start login at its limit or the default login, and got that login's limit. Claude Code refreshes the token as it comes up and holds the login's refresh lock meanwhile, so the SessionStart hook's move was deferred (`move deferred by hook: source login is refreshing`) until the first status-line report, and a print-mode session was not moved at all. The hook now waits for the refresh, at most 9 s, and then moves the session, before its first request.
- **Fixed:** A Fable start on Linux and WSL no longer moves the Fable store. While the store's account was no start login, each start switched the store to a start login, one at its Fable limit included, and held it there until the session was up: every Fable session on the store ran on that account meanwhile and could answer `You've hit your Fable limit`, and a start that took longer than the 30 s hold came up without Fable. A session with a link of its own now takes a login that already sits on a start login with room: the store itself, or else the default login, where it only comes up (`Fable store: Account-N is no start login; starting on the default login.`) and nothing is switched or held; its SessionStart hook moves it to the Fable store. With neither on a start login with room the store is switched as before. The hook now places a session by the model family `start` read when Claude Code names no model, as in print mode: a print-mode Mythos or Fable session no longer stays on the login it came up on. `--account` and a start without a link switch the store as before.
- Every merge to main that adds an entry to `CHANGELOG.md` is released, and nobody names a version any more: the release's notes are the entries the newest tag lacks, and its version is that tag's with the patch number raised when every one of them starts with `**Fixed:**`, else the minor number (after v0.24.1, v0.24.2 or v0.25.0). Entries go at the top of `## Since v0.24.1`, which is never renamed; `## Unreleased` is gone, and the pull request check (`make release-check`) prints what the merge will release or refuses, saying where the entry goes. When merges are released out of order, one release carries all their entries. A release no longer waits about 15 minutes for a Mac runner that does not come: the `macos` check runs in its own workflow, and a release waits for it only while it runs; a macOS job that ran and failed still holds the release.

## v0.24.1

- **Fixed:** A Mythos start on Linux and WSL, fresh or a resume, begins on a start login again, even one at its limit while another Mythos login has room, and its SessionStart hook moves it on: a resume to its recorded login while that has room, else to the selected Mythos login with room. Since 0.20.0 it linked straight to the selected login, or for a resume to its recorded one, whose organization's managed settings can leave out Mythos, so the session came up as Opus. A print-mode session, which draws no status line, now leaves the start login too. The start says `Starting on start login Account-N, which is at its limit; auto-switch moves the session to a Mythos login with room once it is up.`; `--account` of a start login at its limit, and with start logins marked a resume whose recorded login is at its limit, are no longer refused while another login has room.

## v0.24.0

- Releases publish themselves: a merge to main whose `CHANGELOG.md` names a new version (`## vX.Y.Z`) is tagged on its merge commit once CI passed there, and published with that section as its notes. A release appears with its Linux and Windows binaries and `SHA256SUMS`; the macOS binaries follow when a Mac runner has built them, and `SHA256SUMS` then lists them too, every earlier line unchanged. A pull request's check (`make release-check` locally) refuses a version that is not greater than every tag, repeats one, has no entries, is not `vMAJOR.MINOR.PATCH` or comes with a second new version, and any change to a section main already has. The entries written before this release keep their words under `## v0.23.3 and earlier`.
- **Fixed:** a release binary on macOS was offered a release whose macOS build was not attached yet: the update notice, the dashboard's Updates card and the tray announced it, and `tycswap upgrade` then failed with `SHA256SUMS has no line for tycswap_<version>_darwin_<arch>; refusing to install an unverifiable build` (exit 1). A newer release now counts for a release binary only once its `SHA256SUMS` lists this machine's build: until then nothing announces it, and `tycswap upgrade` prints `tycswap 0.23.3 is the latest version for this machine: tycswap 0.24.0 is released, but its build for this machine (tycswap_v0.24.0_darwin_arm64) is not published yet. Try again later.` and exits 0. Builds from source (`go install`, a checkout) are told about the release as before.
- CI and Release jobs that GitHub cancelled because no runner took them (cancelled before their first step, as macOS jobs were for hours on 2026-11-25) are rerun by the Retry workflow until they run; a job that ran and failed is left to a person.

## v0.23.3 and earlier

- **Fixed:** Moving a session to the Fable store no longer waits for tycswap's own store lock while an account belongs to a former session profile or a session group. Since 0.20.0 the decision waited about 10 seconds for each such account, twice, with the store lock held, so other tycswap commands waited too: `tycswap use fable` and the dashboard's move to the Fable store then failed with `timed out preparing the session move`, and the tick, the status line and the allocation answer moved the session about a minute late. The move is now decided at once (one tick placement on a test fixture: 60 s before, 0.1 s after), on the owned accounts' credentials; the empty credential it read before changed no placement. A tycswap process that asks for a lock it already holds now gets the refusal at once instead of waiting for itself.
- The dashboard service reads what no running session owns once per state build: the Fable store's start check, the Mythos selection and each login's verified owner are no longer read again for every linked session and destination, and the Auto tab is computed once. A build costs the same with 12 linked sessions as with one; on a test fixture with 12 it took a tenth of the time.
- `tycswap recovery` without `record` no longer has its own removal line: nothing called it, and it is an unrecognized argument like any unknown command (exit 2). `recovery record`, the hook a former group session may still run, still prints the line and exits 0.
- The dashboard service, the scheduled tick, `status` and `list` read each profile's `.claude.json` and scan its running sessions once per operation instead of once per account and question, and take the account out of a `.claude.json` without decoding the rest of it. With four large session profiles a dashboard state build took about 3.8 CPU-seconds every 5 seconds and a tick 13 to 17.
- A Fable session no longer starts on, or stays on, a Fable store whose logins are all at their limit while the default login's account has Fable room: `tycswap start`, the status line and the scheduled tick put it on the default login, the start notice says why and names the login that comes back first, and the session returns once a Fable login has room.
- `tycswap status`, `tycswap list`, that start notice and one `tycswap.log` warning name the accounts that have Fable room but no Fable login, with `tycswap fable --login`, which signs them in.
- `tycswap fable --login` signs in for Fable every account that runs Fable and has no usable Fable login, one after another: it names each account and waits for Enter, `s` skips and `q` stops, then lists what was signed in, skipped and failed with the reason, and a second run asks only for the rest. The menu's **Sign in for Fable** offers it first when two or more accounts lack a Fable login.
- The accounts that run Fable but have no usable Fable login are named before the Fable pool runs dry, not only once it has: `tycswap status` and `tycswap list` print `Accounts 1 and 4 need a Fable sign-in: tycswap fable --login` where no other Fable hint stands (JSON `fable.withoutLogin`, `fableWithoutLogin`), a Fable start prints it once, and the dashboard shows a header chip, a notice above the accounts and a `no Fable login` chip on each such row.
- Dashboard: status chips in the header (`at limit`, a Fable sign-in) are readable in the light theme. The header is dark in both themes, and its warning and limit chips used the light theme's dark text colours.

- The terminal account menu labels its Mythos sign-in actions **Sign in for Mythos…** and **Sign in again for Mythos…**.
- On Linux and WSL, `statusline.json` gains `logins`, which names the account each login directory (the default login, the Fable store, each Mythos login) holds now, so a status line can show the session's own account instead of the one `~/.claude.json` names for every session.

- When start logins are marked, saving a new account shows the command to include it in future starts.

- `tycswap migrate` resumes an interrupted copy: a rerun copies what is missing, verifies byte for byte what is there, removes a leftover temp file, and refuses only when a path differs from the old store or is not from it. A rerun after a complete copy is a verified no-op.
- Hardening: atomic writers fsync the temp file and the directory, and config backups are written atomically. `settings.json` and `mappings.json` updates hold a lock (`.settings.lock`, `.mappings.lock`) so concurrent commands no longer lose each other's change. `go.mod` pins `toolchain go1.25.14`; `golang.org/x/mod` is raised to v0.40.0 (GO-2026-6179, GO-2026-6180; tycswap does not call the affected code); `make vuln` runs govulncheck.
- Security: strings from exports, APIs and other tools' files (emails, aliases, organization/workspace names, IDE paths) are printed without C0/C1/ESC control characters in `list`, `status`, the dashboard and the Codex commands; `--json` output carries them as stored. `env --shell pwsh` doubles U+2018–U+201B as well as `'`. `add --login` scrubs the auth override variables like `run`/`env`. `add-token` warns when the token is given on the command line, and the docs show the prompt and `-` instead. On Windows, `run` and `add --login` refuse cmd.exe metacharacters in arguments when `claude` is a `.cmd`/`.bat` shim.
- Security: every command refuses a store root not owned by the effective user, naming the path, and makes a root writable by group/other 0700 before it runs; when the mode does not change (a filesystem without POSIX modes, such as a Windows drive under WSL), it warns once on stderr and continues (POSIX). The store lock is opened without following symlinks and without truncation (0600). A stale Claude Code lock directory is broken by rename-then-remove with an age recheck, so two waiters can no longer both hold it; a lock found fresh after the rename is put back without replacing one a third waiter took meanwhile (`renameat2` with `RENAME_NOREPLACE` on Linux). Directories tycswap creates (credentials, `~/.claude`, export parents, lock dirs) are 0700 instead of 0777 before umask. The Claude and Codex HTTP clients no longer follow redirects (a 307 would have re-posted the refresh token); the Claude client caps success bodies at 1 MiB, requires a non-empty string `access_token` and 0 < `expires_in` < 1e7, and logs only the error code of a failed refresh, never the body.
- Security: an inactive account's token refresh (`list`, `status`, dashboard) now takes the store lock before the request, re-checks that the slot is still inactive with no live session, re-reads the backup, and refreshes only when its refresh token is unchanged, as the Codex side does; a concurrent switch or refresh can no longer be overwritten or have its token consumed. `run`/`env` no longer refresh a backup that shares its refresh token with the live login (slot is the current account, or the fingerprints match). `codex login` stores the live auth into its slot before codex replaces it.
- Security: `add` and `add --login` refuse a login whose email cannot name a file, since the email names the account's backup files (`a/../../../x` would name files outside the store): it must hold one `@` between a non-empty local part and domain, at most 254 bytes, and no whitespace, control character, `/`, `\` or `< > : " | ? *`; every real address, an apostrophe or a non-ASCII letter included, is accepted and stored under its raw name. `purge` applies the same check to every `sequence.json` email before it builds a path from one and refuses with the slot named. `import` keeps claude-swap's stricter address pattern for export files. `codex import` validates every row first (email, alias, accountKey) and refuses the file on a bad one; both imports store display fields without control characters.
- `tycswap migrate` copies a macOS Keychain item too large for the `security` command's stdin line (over about 2 KB, as the old tool stored through the command line) to the file tycswap reads for it instead of failing: `credentials/.creds-<n>-<email>.enc[.prev]`, `codex/credentials/<key>.json` or the session profile's `.credentials.json`, mode 0600; the report names the file. The legacy keyring migration does the same with the `.enc` file instead of retrying on every launch.
- Security: on macOS a Claude credential too large for `security -i`'s stdin line (over about 2 KB, reachable with `mcpOAuth` tokens) was passed to `security` on its command line, where `ps` shows it to every local user. The Keychain wrapper now refuses such a payload and the credential is stored in its 0600 file instead (backup `.enc`, `.enc.prev`, or the live `.credentials.json`); the Keychain stays in use for everything else.
- Security: `import` keeps only each account's `oauthAccount` from an export's `config` (a `--full` export included), so an export carrying `mcpServers`, allowed tools or hooks can no longer configure commands on the importing machine; an account without `oauthAccount` is refused. Members are matched exactly and the stored credentials are the bytes that were validated (a `CREDENTIALS` twin used to be stored instead); input over 8 MiB is refused. A switch with no live `~/.claude.json` writes `{"oauthAccount": …}` alone instead of the whole stored config, and a live `~/.claude.json` that exists but does not parse is an error for a switch and for `add-token` instead of being replaced by the few keys tycswap sets.
- `tycswap web [--port N] [--no-open] [--interval SECONDS] [--debug]` serves a browser dashboard on 127.0.0.1: Dashboard (accounts and their actions), Auto (a hosted auto-switch engine with its settings, Next best, quarantine and event log), and Sessions (running Claude Code sessions, including `run`/`env` profiles, with Stop). The printed URL carries a one-time token; redeeming it sets the port-scoped session cookie and hands the page its CSRF token in the redirect's URL fragment, so the browser tab that opened the URL is the only one that can drive the page (a reload keeps it, a new tab needs a fresh URL). Every API call needs cookie and token, mutations a same-origin request, and a foreign Host gets 421. Stop signals a session only after the process start time matches its session file. On Linux and macOS the launch token reaches the browser through a 0600 redirect page in a private directory, never a command line. Export and import stay on the command line.
- The auto-switch engine can retarget its model windows while it runs (`Engine.ApplyModels`), so the dashboard's *Count model limits* applies at once.
- Internal: JSON account listings carry `tokenStatus` when token status is asked for; it was ignored before. Build-time branding vars in `internal/brand` (see `docs/reference.md`, BUILD-TIME BRANDING).
- Security: Keychain service and account names holding a control character (CR, LF, NUL, DEL, C1) are refused before the `security` CLI runs, so a crafted name cannot inject a second command into `security -i`. `import` anchors the email check strictly (a trailing newline is no longer accepted, unlike claude-swap) and refuses whitespace or control characters in email and alias, emails over 254 bytes, aliases over 64 bytes and slots over 999999. Codex exports are written atomically (0600 temp file, then rename) like Claude exports; the log, the usage cache, lock files and session markers are created 0600 under 0700 directories.
- `purge` removes each account's retained `.prev` Keychain item as well as the current one; before, the `.prev` generation outlived the purge on macOS.
- `tycswap upgrade` installs `github.com/tyclab/tycswap/cmd/tycswap@latest`, and the update notice reads tycswap's GitHub releases; before, both pointed at the upstream project. A binary built from a checkout is told `git pull && make install` and nothing is installed. `update.ModulePath`, `update.Endpoint` and `update.ReleasesURL` are settable with `-ldflags -X`.
- **Breaking:** renamed to tycswap. The module is `github.com/tyclab/tycswap`, the binary `tycswap`, the store `~/.local/share/tycswap` (Linux/WSL, `$XDG_DATA_HOME/tycswap` when set) or `~/.tycswap` (macOS/Windows), the log `tycswap.log`, the macOS Keychain services `tycswap` and `tycswap-codex`, and exports are named `.tycswap`. There is no `cswap` alias and no fallback to the old store; `tycswap migrate [--dry-run] [--json]` copies an existing claude-swap store once and never changes it. The startup move of `~/.claude-swap-backup` is gone, and `purge` no longer removes that directory.
- `tycswap add --login [--switch]` runs `claude auth login` in a scratch profile and stores the second account without a logout; the live login stays untouched.
